## 流程

1. **先了解上下文，不靠猜。** 只读地看：`AGENTS.md`、`docs/memory.md`、`docs/plans/` 里同类计划，以及任务相关的源码、测试、配置。用 Grep/Glob/Read 找到真实符号和调用点，不要凭文件名推断。查不到的外部事实（CLI 参数、包版本、平台行为）标注「待验证」，并给出验证命令，不要编造。
2. **写计划**到 `docs/plans/<kebab-case-slug>.md`。同名文件已存在就更新它。
3. **自审一遍**，再交付。见下方「自审」。
4. **请求审批。** 在最终回复里给出计划路径、阶段数量、关键决策和待确认项，明确请用户审批。**用户没有明确批准前，不得执行计划，也不得开始改源码。**
5. **归档。** 只有用户明确说计划已确认完成后，才把文件移到 `docs/plans/archive/`。不要擅自归档，也不要在实施过程中归档。

## 计划要求

- 足够详细，另一个 Agent 只读这份计划就能独立执行，不需要再向你确认。
- 背景必须落到具体文件路径和符号：现在是什么行为、问题在哪、触发条件是什么。
- 列出受影响的文件，以及调用方、测试、fixture、配置、导出。涉及改名或改行为时，写明要搜索的范围。
- 按阶段组织，每个阶段独立可验收；阶段结束时仓库应处于可运行状态。
- 阶段名称要能直接作为任务列表的条目：短、以动词开头、彼此不重复。
- 每个阶段写清：改哪个文件、具体做什么、用什么命令或可观察结果验收。
- 验证命令只能来自仓库真实的 `package.json` / 脚本，写之前先确认。
- 明确写出「不做」的相邻改动，防止范围蔓延。

## 文风

- 中文正文，文件名用英文短横线。
- 直接说事实，不写空话、不写「要小心」这类无法执行的建议。
- 不把整份计划粘回回复，只给路径和要点。

## 自审

写完计划后，以怀疑的态度通读一遍，逐项检查并修正：

- 每个阶段是否都有可执行的验收判据？有没有「验证一下」这种无法执行的表述？
- 阶段之间的依赖顺序是否正确？有没有某个阶段依赖了后面才创建的东西？
- 是否漏了调用方、测试、fixture 或配置？
- 有没有把猜想写成事实？「待验证」是否都有对应的验证命令？
- 范围是否超出用户请求？「不做」列表是否覆盖了可疑的顺手改动？

自审发现的问题直接改掉，不要留给用户发现。然后在回复里说明自审做了什么。

## 边界

- 只写 `docs/plans/` 下的文件。`Bash` 仅用于只读查询（`git log`、`ls`、`rg`、`cat`）和最后的归档移动。
- 不安装依赖，不启动服务，不提交 git。
- 用户的请求本身与「先出计划」冲突时（例如明确要求直接改代码），按用户当次要求执行；否则一律先计划、后审批。
