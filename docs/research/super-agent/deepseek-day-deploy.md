# DeepSeek Super-agent 开源：Router/Worker 双层架构怎么跑

- 来源：DeepSeek V4 Pro Team（独立技术社区，与 DeepSeek 官方无隶属关系）
- 日期：2026-11-02
- 原文：https://deepseek.day/zh-cn/blog/deepseek-super-agent/

## 引言

搜 DeepSeek Super-agent，会看到落差很大的两种说法：一种说它是「又一个 Claude Code 杀手」，另一种说它「只是个实验原型」。两种都不算错，但决定你要不要动手的是后一句里的一个词：原型。

2026 年 10 月 31 日晚，DeepSeek Harness 团队在官方公众号发布《Super-agent 设计探索：迈向更自主的 Agent 系统》，同步在 GitHub 开源了名为 `dsh-superagent` 的 v0.1.0 研究原型（MIT 许可）。官方在设计文档里写得很明确：这是面向工程实践的架构思路探讨，不是对现有产品功能的介绍；公开的代码是实验原型，不是正式商业产品。本站是独立技术社区，下面的事实以官方设计文档与开源仓库为准，不替官方做产品承诺。

它要解决的问题其实不在模型能力，而在人的注意力：一个人通常只能同时跟进 3–5 个活跃会话。当模型已经能独立完成单个任务，多任务的上限就从「模型能不能做」变成了「人能不能盯」。Super-agent 的思路是把会话管理与上下文同步从人手上移到系统层——人只管设定目标和验收结果。

## 一、Super-agent 是什么，不是什么

| 说法 | 实情 |
|---|---|
| 正式商业产品 / 可直接采购 | 否。官方称其为工程探索，代码是 v0.1.0 研究原型 |
| 新的底层模型 | 否。是跑在 DeepSeek Harness 之上的一层 Agent 编排 |
| 闭源、只能调 API | 否。原型以 MIT 许可开源，可自行部署与改造 |
| 能管理多个仓库 | 否。v0.1.0 面向单个 GitHub 仓库 |
| 无需配置就自动改代码 | 否。授权默认是 `observe`，只记录不执行 |
| 已经在自己日常研发里跑 | 是。官方称内部实例已参与问题修复、代码审查与 Harness 自身迭代 |

一句话：它省的是人的注意力，不是 token。后者反而会涨，第五节有具体数字。

## 二、Router 与 Worker 双层架构怎么分工

整套设计只有两层，但职责切得很干净：

- Router（常驻协调层）：长期运行，统一接收群聊、GitHub、邮件、日历提醒、CI 结果等多渠道消息，维护共享上下文，并用轻量模型决定把什么分派给谁。它不做重活，只做判断与派发。
- Worker（隔离执行层）：每个工作项是一个 Ticket，带一条不可变的 mandate。Worker 各自维护独立上下文，并行执行问题复现、代码审查、功能开发，必要时还能再调 Subagent。

两层之间有两个容易被忽略的机制：

1. 订阅（subscription）：PR 上的后续评论直接路由到已分配的 Worker，不必重新走一遍调度判断。这避免了「同一件事被重复评估」的浪费。
2. Watchdog：独立监控任务是否在正常推进，或在无效循环里空转，发现卡住就介入尝试修复。多会话并行最容易死在这里，官方把它单独拎出来做一层。

事件流是事件驱动的：AI 在没人 @ 的情况下也能从群聊里识别潜在缺陷，在后台复现并尝试修复。这也是为什么它的默认授权必须是保守的——下一节讲。

## 三、跑起来要什么环境

`dsh-superagent` 不是 `npm install` 就能用的独立 CLI，它作为 DeepSeek Harness 的 bundle 运行：在本地环境里通过指定的 Harness profile 装配，然后监听 GitHub（可选再监听飞书），把允许的请求转成并行的工作项。

依赖门槛不低，装上之前先对一遍：

| 依赖 | 版本要求 |
|---|---|
| Node.js | 22.19+ 或 24+ |
| git | 2.32+ |
| Python | 3.8+ |
| tmux | 需要 |
| GitHub CLI | 2.48+ |

`tmux` 和 GitHub CLI 出现在依赖里，其实说明了它的工作方式：每个 Worker 是一个独立终端会话，任务推进靠 GitHub 的 PR / 评论串起来。所以它天生偏向 Linux / macOS 的本地或容器环境，Windows 上要先进 WSL。

Harness 本体还没装过的话，先看 DeepSeek Harness 是什么。如果你已经在跟 Harness 的版本节奏，注意 Super-agent 是独立的 bundle，不随 Harness v0.2.1-alpha.2 的插件清单一起发。

## 四、三档授权：off、observe、auto

这是全篇最该先看的一段。一个能在没人 @ 的情况下自己动手的 Agent，权限设计比能力更重要。

| 模式 | 行为 | 适用 |
|---|---|---|
| `off` | 完全不接管 | 只想观察架构、不想连仓库 |
| `observe`（默认） | 记录「它本来会执行的动作」，但不真正执行 | 首次接入、评估风险 |
| `auto` | 直接执行 | 信任已建立、且有 PR 审阅兜底 |

默认给 `observe` 是个很克制的选择：你先跑一两周，看它打算做什么，再决定要不要放开。建议的推进顺序也是这三档——不要一上手就 `auto`。

另外，v0.1.0 的范围是单个仓库。想让它跨仓库协作，目前得自己改代码，不是配置项。

## 五、代价：会话更快了，token 更多了

官方给了一组模拟数据，条件是有噪声的群聊环境。这组数字值得单独看，因为它把「快」和「贵」同时摆出来了：

| 指标 | Super-agent | 传统单会话基线 |
|---|---|---|
| 任务完成时间 p50 | 12.4 分钟 | 官方未披露 |
| 任务完成时间 p95 | 15.7 分钟 | 29.5 分钟 |
| 缓存读取 token（校正后） | 31.77 M | 23.23 M |
| Router 决策量 | 约 +30% | 基线 |

差额很直白：p95 从 29.5 分钟压到 15.7 分钟，代价是缓存读取 token 多约 37%。原因也不难理解——多个 Worker 各自维护独立上下文，前缀复用被切碎了。

还有一组吞吐数据：当事件到达率从每分钟 1 条升到 40 条时，批处理仍能维持吞吐，但单请求延迟从 2.5 秒升到 3.9 秒，批大小从 1.0 涨到 2.8。也就是说峰值压力被批处理吸收成了延迟，不是被消化掉了。

按这个结构算账，成本主要落在缓存读取上，而这恰好是可以优化的部分。前缀设计、system 提示复用和缓存命中的关系，见 DeepSeek API 上下文缓存；如果是多实例并发、担心打满限流，先看 API 429 限流与并发。

## 六、它和 Harness、Claude Code 是什么关系

三者的位置不一样，别混：

- DeepSeek Harness 是运行时和脚手架，模型、工具、会话都在它里面跑。
- dsh-superagent 是跑在 Harness 上的一个 bundle，额外加了 Router / Worker 编排层。
- Claude Code、Codex、OpenCode 是别人家的客户端，你让它们把 DeepSeek 当后端模型用。

所以它不是在跟 Claude Code 抢同一个位置。真正对应的对比对象是各家「多 Agent 编排」的那一层——把人从会话管理里摘出去，而不是把人从写代码里摘出去。

## 常见问题

**能用在生产吗？** 官方定位是研究原型，v0.1.0、单仓库、MIT。适合拿来做内部实验和二次开发，不适合直接压生产流程。

**一定要用 DeepSeek 的模型吗？** 原型是按 Harness 的模型接口写的，Router 明确用轻量模型做分派。理论可换，但要自己改，官方没有提供多模型适配承诺。

**为什么不直接开 `auto`？** 因为它的触发源包括群聊和 CI 结果，误判的代价是真实的代码改动。`observe` 模式先跑一轮，成本最低。

**和 Harness 的版本升级会冲突吗？** 它是独立 bundle，跟着自己的版本走。Harness 升级后建议先在 `observe` 下复跑一次，确认 Ticket 拆解没有走样。

## 总结

DeepSeek Super-agent 的真正主张不是「AI 自己写代码」，而是「AI 自己管会话」。Router 负责判断与派发，Worker 负责隔离执行，Watchdog 兜住空转，授权默认停在 `observe`。

要动手的话，路径很短：装齐 Node 22.19+ / git 2.32+ / Python 3.8+ / tmux / GitHub CLI 2.48+，通过 Harness profile 装配 `dsh-superagent`，先在单仓库上以 `observe` 跑两周。先看它打算做什么，再决定放开到哪一档。至于 token 涨 37% 这件事，是架构的固有代价，不是 bug——优化它得从前缀复用下手。
