# Agent在变强，但“不让它乱来”的那层东西才是真正的进展

- 来源：稀土掘金
- 作者：Jimi1176
- 日期：2026-11-02
- 原文：https://juejin.cn/post/7703423062712631346

10月31日晚上，DeepSeek Harness团队在公众号发了一篇架构文章，公开了Super-agent的设计思路和开源原型。第二天，各家科技媒体的标题集中在“AI自己找Bug提交PR”“没人@也能干活”上。这些描述没错，但漏掉了一个更值得琢磨的细节：Super-agent的五大模块里，有一个叫“外部Watchdog”。

一个自主Agent系统，专门配了一个从外部盯着它的组件。DeepSeek团队自己的说法是，他们让系统在底层接管会话管理和上下文同步，使人从执行细节上移到“决策与验收”。换句话说，Agent越自主，人越需要退到外面去，而那个“外面”的位置，必须有东西占着。Watchdog占的就是这个位置。

这一周值得写的东西不少：MCP协议在10月30日正式移除了协议级会话，Salesforce给Agent加上了硬性预算和Kill Switch，微软和伯克利放出了一个不改Agent代码就能把成本砍掉两三成的插件。单独看每一条都是产品更新或论文发布，但如果把它们摆在一起，会发现一个共同的姿态：2026年10月底的Agent工程，正在把越来越多的东西从模型内部“搬出去”。

## Watchdog不是保险丝，是承认模型不知道什么时候该停

先把这个细节说透。DeepSeek的Super-agent采用Router和Worker双层设计，Router负责接收消息、理解任务之间的关系并分派，Worker负责具体执行。事件驱动机制让工作环境中的消息也能成为任务的起点，而不是只有人类发指令才启动。这些设计解决的是“Agent怎么同时跟进多件事”的问题。但多任务并行带来的副作用是：一个Agent可能在多个方向上同时推进，而它自己没有一个可靠的内部信号来判断“哪个方向已经跑偏了、哪个任务应该被叫停”。

外部Watchdog的存在，本质上是在说：模型自身的置信度和自我评估，还不足以作为停止或干预的唯一依据。你可以在Prompt里写“遇到不确定的情况请停下来询问”，但模型在生成长链条的推理和执行中，对“自己是否已经不确定”的判断，本身就是不可靠的。一个在第三轮就应该停下的任务，模型可能在第三十轮还在自信地继续。Watchdog从外部监控行为模式——响应时长、工具调用的重复率、输出长度的异常增长——而不是依赖模型自己报告“我卡住了”。

这和TokenEconomizer里的“loop guard”是同一个思路的不同实现。TokenEconomizer的做法更轻：当一个turn反复撞上相同的失败时，一个judge模型判断是否“卡住了”，如果置信度超过0.7，就给Agent注入一条简短的提示让它换条路，每个turn最多一次。它自己从不停止一个turn，只告诉用户该怎么停。这个设计选择很说明问题：工具的作者不信任Agent能可靠地自我中断，但也不认为外部干预应该粗暴地接管。干预的权限被刻意限制在“提示”和“告知”上，而不是“执行”。

## MCP把“会话”删了，因为没人说得清它到底是什么

10月30日的MCP规范更新里，SEP-2567正式生效：协议级的session概念被移除，`initialize`握手和`Mcp-Session-Id`头被删除，跨调用的状态改由服务端铸造的显式句柄来携带。

这个变更的理由写得很坦率。提案里说，sessions在规范里存在了一年多，但客户端对它的理解从未收敛：有的按单次工具调用来划定session的范围，有的按应用启动，有的按页面加载，而“几乎没有客户端会恢复一个session”。一个服务端作者在把服务接到任意客户端时，无法预测这个session会活多久、范围多大，这使得session作为应用状态的容器变得不可靠。

与其继续维护一个语义模糊的协议抽象，不如把它拿掉，让模型自己携带一个显式的`basket_id`或`browser_id`，在后续调用中把它当作普通工具参数传回去。状态不再藏在协议层的一个隐式容器里，而是变成模型可以看见、可以决定传递还是丢弃的显式对象。

这是一个比“简化协议”更深层的转向。隐式会话的问题不在于它“多了个功能”，而在于它把状态的归属权放在了一个语义不确定的位置上。当Agent出错时，你很难判断问题出在模型的决策上，还是出在session在某个客户端里意外地提前失效或错误地延续了。把状态显式化之后，至少归因的链条变短了。代价是模型需要承担更多管理状态的责任，但这个责任至少是可见的、可审计的。

## 成本控制的重心，从“看账单”移到了“拦住请求”

Salesforce在10月27日给Agent Fabric加的三个成本控制功能，值得从“干预发生在哪个时间点”的角度来看。FinOps Dashboard提供花费的汇总视图，Model Wallet设置硬性支出上限，在请求发出之前就把它拦住，Cost Optimization Policies声称在测试场景中能把Token使用量降低最多75%，靠的是语义缓存和payload压缩。

这三层里，真正改变成本治理逻辑的是Model Wallet的“stop requests before a budget is exceeded”。传统的成本管理是事后性的：月底看账单，发现某个Agent工作流的消耗异常，再去排查。但Agent的失败模式往往不是单次调用贵，而是失败循环在短时间内烧掉大量Token。事后看到账单时，钱已经花完了。硬性预算拦截把干预的时机推到了请求发出之前，这意味着成本控制从“财务审计”变成了“运行时约束”。

同一周，Salesforce还加入了Agent Kill Switch的触发版本：当Agent Evals检测到质量低于阈值时，自动触发干预。成本和质量的干预被放在了同一个控制层里，而不是由两个团队分别盯着两张报表。这个整合本身可能比任何一个单独的功能都更有信号意义：Agent治理正在从“出问题后分别响应”转向“在同一个执行路径上预先约束”。

## 一个被排行榜掩盖的事实：分数是harness的函数

还有一个这一周发生的、不太像“新闻”但很能说明问题的事。Kimi K3.1 Pro在Terminal-Bench 4.0上的分数，在三个不同的榜上读出了三个数：Artificial Analysis的页面显示67.2%，Vals AI用Mini-SWE-agent跑出63.64%（排第三），Moonshot自己的博客用Claude-Code harness报告65.7%。同一个模型、同一个benchmark，分数差了3.6个百分点，排名从第一到第三。

Vals的表格里还有一组数字：Kimi K3.1 Pro每测试成本4.57美元，Opus 5.5每测试成本13.20美元，后者的分数是65.15%。如果只看“谁第一”，Kimi在AA的榜上是第一；如果看“每美元买到多少通过率”，Kimi在Vals的榜上是头部里最便宜的；如果看“和Claude Code这个具体harness搭配时的表现”，它落后Opus 0.7分。三个问题，三个答案，各自都是真实的。

这件事的直接含义很简单：benchmark分数不是一个模型的属性，是模型×harness×评测方法的联合输出。更深一层的含义是，当模型能力的差距缩小到一两个百分点时，harness的选择对最终表现的影响，可能比模型之间的差距更大。一个团队如果因为“TB4第一名”的标题就把流量切过去，而自己的生产harness恰好是Vals那一套，实际表现可能和标题暗示的完全不是一回事。

## 把这几件事放在一起看

Watchdog、无状态MCP、硬性预算拦截、harness敏感的分数——它们各自解决的是不同层面的问题，但有一个共同的指向：Agent系统的可靠性，正在越来越依赖模型外部那层“不让它滑出去”的结构，而不是模型自身“知道自己该在哪停”的能力。

DeepSeek团队在文章末尾说了一句很克制的话：他们没有提出全新理论，只是把任务调度、事件驱动、存算分离这些经典系统思想用到了Agent架构上。这句话本身就在承认一件事：Agent工程当前面对的很多问题，不是等下一个更强的模型就能自动消解的。调度、状态管理、故障隔离、预算约束，这些是系统问题，模型变强不会让它们消失，只会让它们暴露得更充分——因为Agent跑得越久、管的事越多，一个模糊的session语义或一个缺失的外部中断机制造成的代价就越大。

如果这一周的信息里有一个值得带走的判断框架，大概是这个：下次看到一个Agent系统宣称“自主性提升”时，问一句它的Watchdog在哪、状态是怎么携带的、预算在哪一层被拦住。如果这三个问题的答案都是“模型自己会处理”，那这个系统在demo里可能很好看，在生产里大概率会遇到一些模型自己解决不了的问题。
